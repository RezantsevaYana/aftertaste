# Архитектура фронтенда Aftertaste

## Аккаунт и настройки — 4 ноября 2026

`api/account.ts` содержит запросы настроек; `stores/preferences` владеет
загруженными категориями, их включением, правилами рецензий и `plansVisible`.
Черновик новой категории остаётся в `CategoriesSettings`, остальные изменения
сохраняются сразу. `PrivacySettings` меняет правила категории; запись хранит
исключение `reviewVisibility: inherit | private | friends`. Это подготовка
к обмену: серверный доступ к записям по-прежнему ограничен владельцем.

`ProfilePage` собирает профиль, пароль, категории и приватность и проверяет
`canLeave` активного раздела. `App.vue` владеет текущим разделом каталога
(`activeSection`), передаёт его через `CatalogPage v-model:section` и проверяет
уход из кабинета перед навигацией. Временная исходная шапка открывает коллекцию
в разделе впечатлений; выбор планов остаётся во вкладках каталога.

Прежний список из шести видимых категорий расширен: добавлены `concert`,
`podcast`, `lecture`, а также `custom` с обязательным `customCategoryId`.
Музыка продолжает объединять song/album. Стор формирует видимые категории
и варианты формы; выключенные исключаются из каталога и счётчиков без удаления
данных. Текущая выключенная категория доступна при редактировании записи.

Backend-модуль `account` защищён AuthGuard. Миграция
`20261103000000_account_settings` добавляет настройки пользователя,
`CategorySetting`, `CustomCategory`, ссылки восстановления и поля записей.
Своя категория уникальна по нормализованному названию у владельца; API записей
проверяет её принадлежность при создании, изменении и импорте.

`PasswordResetService` управляет одноразовым токеном и транзакцией сброса,
`MailerService` отправляет письмо через Nodemailer SMTP. Сырой токен только
в письме, в БД SHA-256; сброс отзывает все сессии. Отправка асинхронная без
постоянной очереди. `App.vue` считывает и очищает resetToken из URL,
`pages/auth` показывает реальные состояния восстановления. Локальные письма
принимает Mailpit. API, SMTP-конфигурация и ограничения — в [AUTH.md](AUTH.md).

## Планы и завершение записи

План и впечатление — одна сущность `Entry` с `status: done | plan`.
В TypeScript статус необязателен для совместимости: отсутствие означает `done`.
PostgreSQL использует enum `EntryStatus` и default `done`, поэтому старые записи
остаются впечатлениями. Миграция `20261027000000_entry_plans` добавляет статус,
индекс и `plannedDate`, разрешает NULL у `rating` и `month`. CHECK сохраняет
инвариант: у плана `rating`, `month`, `date`, `dateStart` — NULL; у впечатления
есть оценка 1–10 и месяц.

`plannedDate` — отдельная необязательная дата YYYY-MM-DD, один день даже для
книг и сериалов. Она не заменяет фактические `date`/`dateStart` впечатления.
Заметка плана хранится в `review`; фотографии и индекс главной фотографии
используют существующие поля. План требует название и категорию; исполнитель
песни или альбома становится обязательным при завершении.

`useCatalog` использует переданный ref раздела, владеет списком и сценарием завершения. `CatalogSections`
показывает общие счётчики, `EntryList` группирует планы по наличию даты и
сортирует датированные по возрастанию. Утилиты `entities/entry/model/date-filter.ts`
применяют дату/год к `plannedDate`; планы без даты исключаются при таком фильтре.
При смене раздела сохраняется категория, очищаются поиск, дата и год.

Действие карточки или деталей открывает `EntryFormModal` в режиме завершения.
Оценка начинается с 0 и требует явного выбора; фактическая дата обязательна,
для книг и сериалов форма использует период. Сохранение через `updateEntry`
меняет статус той же записи на `done`, сохраняя id, plannedDate, фото и review.
До сохранения исходный план не изменяется; действует подтверждение закрытия
изменённой формы. Ошибки запросов оставляют данные формы доступными.

Для отката `useCatalog` держит исходный план в памяти. «Отменить» отправляет
его через API и обновляет список после успешного ответа. «Посмотреть» переключает
раздел, снимает поиск/даты, при необходимости выбирает категорию записи,
прокручивает и фокусирует её карточку. Данные сохраняются в PostgreSQL;
моки планов из отдельного прототипа в основной каталог не подключены.

## Общий подход

### Автор, режиссёр и жанр

`ContentType` содержит семь сохраняемых типов записей. Миграция
`20261027030000_entry_songs` добавляет `song` в PostgreSQL enum без изменения
прежнего `album` и его записей. Видимых категорий шесть: `CatalogCategory`
объединяет song/album в `music`. `catalogCategories` задаёт кнопки каталога,
`getCatalogCategory` отображает сохраняемый тип в категорию интерфейса.
Фильтр «Музыка» включает оба типа; завершение и переход к записи используют
это же отображение. Новый UX не меняет API, схему или записи базы.

Предметный helper `isMusicType` объединяет `song` и `album` в форме, карточках,
деталях и совместимом преобразовании старых API-данных. Песня имеет отдельное
название, исполнителя, одну дату прослушивания, оценку,
review и фотографии. Исполнитель обязателен для впечатления, необязателен для
плана. Пресеты жанров у песен и альбомов общие, сохранённые пользовательские
подсказки для формы объединяют оба музыкальных типа. Сам genre остаётся строкой
конкретной записи. Правила автора и режиссёра не меняются.
Форма разделяет выбор категории и музыкального формата из `musicFormats`
(«Трек»/«Музыкальный альбом»). Новый объект музыки получает song, редактируемый
альбом сохраняет album. В пределах одной формы выбор формата помнится при
переходе к другой категории и обратно; смена трек/альбом сохраняет artist/genre.
Завершение песни — «Прослушано», с тем же id и существующим откатом плана.
`EntryImage` использует для song прежний `category-covers/avant-garde-v1/album.jpg`.

`EntryDraft` и Prisma `Entry` дополнены необязательными строками `author`,
`director`, `genre` (до 200 символов). Миграции `20261027010000_entry_author_genre`
и `20261027020000_entry_director` добавляют nullable VARCHAR(200); прежние записи
не требуют заполнения. Сервер проверяет поля и отображает их в API-модель.
Автор относится к книгам, режиссёр — к фильмам, сериалам и спектаклям, новый
жанр — к книгам, фильмам, сериалам, песням и альбомам. Прежний enum `theatreGenre`
остаётся отдельным, выставки не получают новый жанр.

`entities/entry/model/genres.ts` хранит пресеты и собирает подсказки из жанров
сохранённых записей по типу, удаляя повторы без учёта регистра; музыкальная
форма объединяет подсказки song/album. Отдельного
глобального справочника нет: произвольный жанр хранится строкой в самой записи.
`BaseSelect` с `allowCustom` поддерживает ввод и выбор; обычный режим остаётся
списком. Стрелки/Enter управляют вариантами, пробелы и каретка работают нативно.
Escape закрывает раскрытый список до обработки модалкой. Tab/blur сохраняет
текст, обрезает крайние пробелы и нормализует известное значение по подсказке.

Форма сбрасывает жанр при смене категории (сохраняет между song/album) и исключает неприменимые метаданные из
сохраняемого draft. Карточки и детали показывают заполненные поля. Завершение
плана и восстановление исходного плана сохраняют эти данные существующим
потоком обновления записи. Плавающие подписи формы не содержат «необязательно»;
это требование к тексту подписи, а не к обязательности полей.

Используем собственную модульную архитектуру с идеями FSD. Это не строгая FSD:
сторы и доступ к данным собраны в отдельных корневых папках, компоненты и
composables страниц названы явно. Выбираем понятные границы ответственности
и удобство самостоятельной работы. Сервер сохраняет структуру NestJS.

## Сторы

Все сторы размещаем в `stores`, группируя по назначению:
`stores/catalog/useCatalogStore.ts`, `stores/auth/useAuthStore.ts`,
`stores/modals/useModalStore.ts`. Эти модули создаём по мере реализации;
сейчас реализованы `stores/auth` и `stores/preferences`,
а `stores/index.ts` создаёт экземпляр Pinia. Стор модалок остаётся будущей работой.

В стор выносим только необходимое общее состояние и операции над ним.
Не переносим туда автоматически все переменные и всю логику. Черновик формы
остаётся в форме; поиск и управление текущими модалками — в `useCatalog`.
У списка записей должен быть один владелец: если переносим его в стор,
не оставляем вторую изменяемую копию в composable страницы.

Composable с локальными refs создаёт новое состояние при каждом вызове.
Pinia-стор разделяет состояние между потребителями одного экземпляра Pinia.
Сам Pinia не сохраняет данные после перезагрузки страницы.

## Компоненты и composables

Компоненты только одного экрана — в `pages/<страница>/components`.
Его composables — в `pages/<страница>/composables`.
Другие страницы не импортируют внутренний код этой страницы.

Общие технические composables без знаний о каталоге — в `shared/composables`
(папку создаём с первым таким composable). Обычные функции без Composition API,
например форматирование месяца, — в `shared/lib`.
Логику предметной области, нужную разным страницам, размещаем в соответствующем
модуле сущности или отдельном модуле пользовательского сценария; не складываем
её в `shared` только из-за переиспользования.

Общие визуальные компоненты разделены на `shared/ui/buttons`, `form`, `modals`.
Форма добавления записи остаётся в каталоге: она знает поля и правила записи.
Конкретные шапка и футер Aftertaste — в `app/layout`. Оболочка подключается
в `App.vue`, чтобы страницы не зависели от `app`.

## Доступ к данным

`api/catalog.ts` содержит HTTP-запросы к NestJS (`GET/POST/PUT/DELETE
/api/entries`). Сервер хранит записи в PostgreSQL через Prisma. Схема и миграции
находятся в `backend/prisma`. Каждая новая запись получает владельца из
серверной сессии; операции чтения, изменения и удаления ограничены его id.
Прежние анонимные записи удалены по запросу пользователя. Автоматическое
заполнение демозаписями и перенос из JSON/localStorage отключены. В Docker
Adminer доступен только локально на порту `8081`.

Общий HTTP-клиент — `api/http.ts`: отправляет cookie и защитный заголовок,
возвращает результат или выбрасывает ApiError. При 401 каталога отправляет
техническое событие истечения сессии; `App.vue` связывает его с auth-стором.
API не импортирует сторы или UI. Ошибки полей и конкретного сценария остаются
в этом сценарии. Если данными владеет стор, запрос и обновление состояния
выполняет его действие.

`api/auth.ts` отвечает за HTTP-запросы аккаунта, `stores/auth` — за пользователя,
проверку сессии, вход и выход. `pages/auth/AuthPage.vue` содержит форму входа и
регистрации в два шага. `pages/profile/ProfilePage.vue` содержит редактирование
имени, фамилии и аватара; загрузка изображения вынесена в общий AvatarInput.
App.vue показывает авторизацию до входа и монтирует каталог только после
успешной проверки. Правила Vuelidate остаются в форме. Подробности сервера,
сессий, CORS и proxy trust — в [AUTH.md](AUTH.md).

## Модалки: отдельная будущая итерация

В этой итерации перенесены только общие компоненты модалок. Управление ими
осталось в странице каталога, существующие props и события сохранены.
Стор модалок, callbacks и общий компонент их отображения пока не реализуем.

Будущая система будет управлять открытием, текстом и переданным действием,
очищать их при закрытии. Реализация действия (например, удаление записи)
остаётся в соответствующем модуле. Детали асинхронного подтверждения,
хранения обработчиков и нескольких одновременных окон обсудим отдельно.

## Границы зависимостей

- `app` собирает оболочку, страницы и подключает Pinia.
- Страницы и их composables используют сторы, API, сущности и общий UI.
- Сторы могут использовать API и модели сущностей, но не страницы и компоненты.
- API использует модели данных и общие технические функции, но не сторы и UI.
- Сущности не зависят от страниц, сторов и API; `shared` не знает предметную область.
- Между страницами нет импортов. Циклические зависимости не допускаем.

Для модулей с публичным `index.ts` внешние импорты идут через него:

```ts
import { EntryCard, type Entry } from '@/entities/entry'
import { BaseButton, ConfirmationModal } from '@/shared/ui'
import { loadEntries, saveEntries } from '@/api/catalog'
```

Внутри модуля используем пути через алиас `@/`, не собственный публичный index.
Например: `@/pages/catalog/components/EntryDetailsModal.vue`.

## TypeScript и стили

### Валидация форм

`MonthPicker` оборачивает `@vuepic/vue-datepicker` в режиме выбора месяца
с русской локалью и моделью `YYYY-MM`. Палитра библиотечного меню задана
CSS-переменными в `main.scss`. Самописной сетки календаря нет.
Меню селекта и календаря позиционируются через Floating UI с `fixed`,
`flip` и `shift`. `usePopupTarget` направляет Teleport в текущий native dialog
(или `body` вне модалки), чтобы меню оставалось в доступном верхнем слое.
Меню не участвует в потоке формы; при нехватке места снизу открывается вверх.

Форма записи использует `@vuelidate/core` и `@vuelidate/validators`.
Правила принадлежат форме: общий UI не импортирует Vuelidate и получает
готовое сообщение через необязательный prop `error`. Это поддерживают
`BaseInput`, `BaseSelect`, `BaseTextarea` и `RatingInput`.
Поля проверяются после потери фокуса и при отправке формы; до взаимодействия
ошибки не показываются. Перед сохранением вызывается `$validate()`, при
ошибке фокус переходит на первое неверно заполненное поле.
Нативные всплывающие ошибки отключены через `novalidate`.

Сообщение ошибки расположено абсолютно под контролом, место под него
резервируется отступом. Ошибка связывается с полем через `aria-describedby`,
состояние — через `aria-invalid`. Цвета ошибки задаются в `_variables.scss`.
`PhotoInput` отдельно проверяет формат, размер и чтение выбранного файла
и показывает локальную ошибку в том же оформлении.

### SVG-иконки

Общий `BaseIcon` экспортируется из `@/shared/ui` и использует `@iconify/vue`.
В справочниках храним имя иконки Iconify, например `icon: 'lucide:book-open'`,
и выводим `<BaseIcon :icon="type.icon" />`. Для единого оформления используем
контурный набор Lucide. Другую иконку можно выбрать на https://icon-sets.iconify.design/lucide/.

Размер — `1em`, цвет наследуется через `currentColor`. По умолчанию иконка
декоративная; для самостоятельного изображения передаём `label`. У кнопки
только с иконкой доступное название задаём самой кнопке через `aria-label`.
Основные иконки аккаунта, каталога и общих действий включены в локальный
Lucide-набор `shared/ui/icons/account-icons.ts` и появляются без запроса к сети.
`BaseIcon` сначала ищет имя в этом наборе; для остальных имён остаётся загрузка
через API Iconify. Локальный SVG-спрайт не используется.

Отдельный `.ts` не нужен каждому компоненту. Props, emits и небольшая локальная
логика остаются в `<script setup lang="ts">`. Типы записи — в
`entities/entry/model/entry.ts`, сценарии страницы — в её `composables`,
сторы — в `stores`, доступ к данным — в `api`.
Выносим код по самостоятельной ответственности или для переиспользования.

Все SCSS остаются в `src/styles`. Имена файлов — в kebab-case, строчными буквами:
`EntryCard.vue` → `entry-card.scss`. Sass partials сохраняют префикс `_`.
Стили оболочки — в `styles/layout`, каталога — в `styles/catalog`, общего UI —
в `styles/ui`. Глобальные стили и reset — только в `styles/main.scss`.
Порядок блоков Vue: template, script, style. Сохраняем scoped и правила контейнера.
Не создаём пустые файлы и папки для ещё не реализованных возможностей.

### Просмотр фотографий

Плитка `PhotoGallery` открывает стандартный `@lightgallery/vue` с плагинами Zoom и Thumbnail. Native dialog используется только как верхний слой поверх формы, без собственного интерфейса просмотрщика.

Для примерки используется evaluation-ключ lightGallery. Ключ для публикации задаётся через `VITE_LIGHTGALLERY_LICENSE_KEY`. Условия библиотеки: GPLv3 для совместимого открытого проекта либо коммерческая лицензия для закрытого исходного кода: https://www.lightgalleryjs.com/docs/license/.
