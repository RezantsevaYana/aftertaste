# TypeScript: теория и вопросы для собеседований

Краткий конспект по темам, разобранным при разработке Aftertaste.
Примеры упрощены: это не полное описание моделей проекта.

## Интерфейсы и extends

### Краткая теория

`interface` описывает структуру объекта: имена свойств, их типы,
обязательность, а также сигнатуры методов. TypeScript использует это описание
для проверки кода. Интерфейс не создаёт объект, не задаёт значения по умолчанию
и не проверяет данные во время выполнения программы.

```ts
interface EntryDraft {
  title: string
  rating: number
  venue?: string
}

interface Entry extends EntryDraft {
  id: string
}
```

Здесь объявлены два интерфейса. `EntryDraft` описывает данные формы,
а `Entry` расширяет его: содержит те же свойства и обязательный `id`.
Исходный `EntryDraft` не меняется. Если изменить описание общего поля
в `EntryDraft`, это изменение распространяется на `Entry`.

```ts
const draft: EntryDraft = {
  title: 'Гамлет',
  rating: 8,
}

const entry: Entry = {
  ...draft,
  id: 'entry-123',
}
```

`extends` работает с описаниями типов, `: Entry` задаёт тип переменной,
а объектный spread `...draft` копирует собственные перечисляемые свойства
объекта в новый объект во время выполнения. Копирование поверхностное:
вложенные объекты не клонируются, их ссылки сохраняются.

### Вопросы и ответы

**Что такое interface в TypeScript?**  
Описание структуры, которой должно соответствовать значение. Интерфейс
может описывать свойства, методы и, например, сигнатуры вызова функции.

**Существуют ли интерфейсы во время выполнения JavaScript?**  
Нет. Они удаляются при компиляции. Нельзя создать объект через `new Entry()`
или проверить его через `instanceof Entry`, если `Entry` — только интерфейс.

**Что означает extends в объявлении интерфейса?**  
Новый интерфейс включает требования базового интерфейса и может добавлять
свои. Это расширение типа, а не копирование данных или наследование реализации.

**Можно ли расширить несколько интерфейсов?**  
Да: `interface Entry extends EntryDraft, Timestamps { id: string }`.
Требования к одноимённым свойствам должны быть совместимы.

**Можно ли при расширении изменить тип свойства?**  
Можно совместимо сузить его, но нельзя произвольно заменить несовместимым.
Например, свойство `status: string` можно сузить до `status: 'saved'`.
Замена `rating: number` на `rating: string` вызовет ошибку.

**Что означает вопросительный знак в venue?: string?**  
Свойство может отсутствовать. При чтении с включённым `strictNullChecks`
нужно учитывать `undefined`. Возможность явно записать `venue: undefined`
также зависит от настройки `exactOptionalPropertyTypes`.

**Зачем разделять EntryDraft и Entry?**  
У данных новой формы ещё нет идентификатора, а у сохранённой записи он
обязателен. Раздельные типы отражают это различие. Если сделать `id` обязательным
в общем типе, он понадобится и форме; если необязательным — его наличие
не будет гарантировано для готовой записи.

**Можно ли передать Entry туда, где ожидается EntryDraft?**  
Да: `Entry` содержит все необходимые поля. TypeScript использует структурную
типизацию — важна структура значения, а не имя интерфейса. Обратное присваивание
невозможно без обязательного `id`.

**Разрешает ли структурная типизация любые дополнительные поля?**  
Есть нюанс: для свежего объектного литерала TypeScript проверяет лишние
свойства. Например, литерал с `id` при прямом присваивании переменной
типа `EntryDraft` вызовет ошибку. Уже существующую переменную типа `Entry`
можно присвоить переменной типа `EntryDraft`.

**Чем extends отличается от ...object?**  
`extends` расширяет описание типа при проверке кода. `...object` внутри
объектного литерала переносит реальные свойства и значения в создаваемый
объект во время выполнения. Spread не выполняет глубокое копирование.

**Проверит ли interface ответ сервера?**  
Нет. Аннотация типа не валидирует внешние данные. Их проверяют во время
выполнения вручную или с помощью библиотеки валидации.

**Чем interface отличается от type?**  
Оба могут описывать структуру объекта. `type` также позволяет дать имя
объединению, примитиву, кортежу и другим типам. Интерфейсы поддерживают
слияние объявлений с одинаковым именем; псевдонимы `type` — нет.
Интерфейсы расширяются через `extends`, а типы можно комбинировать
пересечением `&`. Пересечение не полностью равнозначно `extends`:
например, несовместимые свойства могут дать тип `never`, вместо ошибки
непосредственно при объявлении расширения.

## Получение типа из массива: typeof, [number], as const

```ts
const contentTypes = [
  { value: 'book', label: 'Книги' },
  { value: 'film', label: 'Фильмы' },
] as const

type ContentType = (typeof contentTypes)[number]['value']
// 'book' | 'film'
```

**Почему нельзя написать type: contentTypes в интерфейсе?**  
В этом примере `type` — имя поля, а после двоеточия нужен тип.
`contentTypes` — переменная со значением. Чтобы получить её тип,
используют `typeof contentTypes` в позиции типа.

**Как разобрать (typeof contentTypes)[number]['value']?**  
`typeof contentTypes` получает тип массива; `[number]` получает тип
элемента по любому числовому индексу; `['value']` получает тип поля
`value` этих элементов. Результат — объединение допустимых строк.

**Зачем нужен [number]?**  
Он переводит нас от массива к его элементам. Без него `['value']`
ищет свойство у самого массива. Для этого кортежа `[0]['value']`
даст только `'book'`, а `[number]['value']` — `'book' | 'film'`.

**Зачем здесь as const?**  
Он сохраняет литеральные типы значений и делает свойства литерала
доступными только для чтения на уровне типов, а массив — readonly-кортежем.
Без него в этом примере `value` расширится до `string`.
`as const` не замораживает объект во время выполнения, как `Object.freeze`.

**Обязательно ли объявлять отдельный ContentType?**  
Нет. Выражение типа можно написать прямо в поле интерфейса.
Имя `ContentType` делает код короче и позволяет повторно использовать тип.

## Утилиты типов: Record и Partial

```ts
const coverImages: Partial<Record<ContentType, string>> = {
  book: '/category-covers/book.png',
  film: '/category-covers/film-camera.png',
  series: '/category-covers/series-clapperboard.png',
}
```

Тип читается изнутри наружу:

1. `ContentType` — объединение допустимых категорий.
2. `Record<ContentType, string>` — объект с обязательным строковым значением
   для каждой категории.
3. `Partial<...>` — делает все свойства полученного типа необязательными.

Для текущих категорий результат соответствует такой структуре:

```ts
type CoverImages = {
  book?: string
  film?: string
  series?: string
  theatre?: string
  album?: string
  exhibition?: string
}
```

Вложенность здесь комбинирует два преобразования типа, а не создаёт
вложенные объекты. Данные остаются плоским словарём «категория → путь».
В EntryImage картинки есть только для части категорий; для остальных
используется оформление через SCSS. Поэтому подходит частичный словарь.

При необходимости выражение можно разделить, не меняя его смысла:

```ts
type CategoryImages = Record<ContentType, string>
type OptionalCategoryImages = Partial<CategoryImages>
```

### Вопросы и ответы

**Что такое Record<Keys, Value>?**  
Встроенный вспомогательный тип TypeScript, описывающий объект с ключами
`Keys` и значениями типа `Value`. Например, `Record<'book' | 'film', string>`
требует оба поля. Ключи должны быть совместимы со `string | number | symbol`.

**Record — это тип или утилита?**  
Это утилита типов (utility type): встроенный обобщённый псевдоним типа.
Эти понятия не противопоставляются. Слово «утилита» описывает назначение:
помогать строить типы из других типов. `Record` принимает два аргумента типа,
например `Record<'book' | 'film', string>`, и описывает полученную структуру.
Это не функция JavaScript: аргументы передаются в `<...>`, а не в `(...)`.

**Как устроен Record внутри?**  
Его определение использует mapped type — отображаемый тип:

```ts
type Record<K extends keyof any, T> = {
  [P in K]: T
}
```

`K` — тип ключей, `T` — тип значений. `keyof any` соответствует
`string | number | symbol`. Запись `K extends keyof any` ограничивает
допустимый аргумент `K`, а `[P in K]: T` описывает свойство типа `T`
для каждого ключа из `K`. Здесь `extends` — ограничение параметра типа,
а не расширение интерфейса. Никакого цикла по данным во время выполнения нет.

**Что такое Partial<T>?**  
Встроенный вспомогательный тип, делающий все свойства `T` необязательными.
Он создаёт новый тип, а исходный не меняет. Не удаляет поля реального объекта
и не меняет тип значения существующего поля на произвольный.

**Partial — это просто замена вопросительных знаков? Есть ли другие функции?**  
Его назначение — сделать все свойства переданного типа необязательными,
то есть по эффекту это `?` у каждого свойства верхнего уровня. Дополнительных
действий с данными он не выполняет. Преимущество перед ручным перечислением:
не нужно дублировать поля, и при изменении исходного типа производный
автоматически учитывает изменения. Частое применение — описание частичного
обновления. `Partial<T>` допускает даже пустой объект, не превращает вложенные
поля в необязательные и не реализует само обновление объекта.

```ts
interface Draft {
  title: string
  rating: number
}

type DraftChanges = Partial<Draft>
// { title?: string; rating?: number }

const changes: DraftChanges = { rating: 9 }
```

**Как Partial используется для частичного обновления?**  
Он описывает объект изменений, в котором можно передать только нужные поля.
Применение этих изменений — отдельная операция JavaScript:

```ts
const draft: Draft = { title: 'Гамлет', rating: 8 }
const changes: Partial<Draft> = { rating: 9 }

const updated: Draft = { ...draft, ...changes }
// { title: 'Гамлет', rating: 9 }
// draft остаётся прежним.
```

`Partial<Draft>` проверяет допустимость объекта `changes`, но ничего
не обновляет. Объектный spread копирует свойства: сначала исходные,
затем изменения. При повторении ключа побеждает более позднее значение.
Это упрощённый пример для определённых значений полей: при разрешённом
явном `undefined` он тоже перезапишет прежнее значение. В настоящем
обновлении правила для отсутствующих полей, `undefined` и очистки значений
нужно определить отдельно.

**Почему здесь недостаточно Record<ContentType, string>?**  
Он потребует пути для всех категорий. В объекте есть только три категории,
поэтому без `Partial` TypeScript сообщит об отсутствующих свойствах.

**Можно ли передать пустой объект в Partial<Record<ContentType, string>>?**  
Да, все свойства необязательные. Такой тип не требует наличия хотя бы одной картинки.

**Какой тип у результата coverImages[type]?**  
При включённом `strictNullChecks` — `string | undefined`: для допустимой
категории путь может отсутствовать. Вызывающий код должен это учитывать.

**Почему не Record<string, string>?**  
Он не ограничивает имена ключей нашими категориями. Например, опечатка `boook`
не будет отвергнута как неизвестная категория. Чтение отсутствующего ключа
такого словаря учитывает `undefined` при включённом `noUncheckedIndexedAccess`.

**Запрещает ли Record любые дополнительные свойства?**  
Не делает объект «точным» типом. Лишние ключи проверяются у свежего объектного
литерала, но структурная типизация в общем случае допускает дополнительные
свойства у уже существующих значений.

**Делает ли Partial вложенные свойства необязательными?**  
Нет, только верхний уровень. Если поле содержит объект и этот объект передан,
его внутренние обязательные поля остаются обязательными.

**Существуют ли Record и Partial во время выполнения?**  
Нет. Это преобразования типов для проверки кода, а не функции JavaScript.
Они не создают объект, не копируют данные и не проверяют входящий JSON.

## Практическое применение TypeScript: ответ на собеседовании

Описывая опыт, связываем механизм типов с задачей и конкретным примером.
Не стоит заявлять регулярное использование инструмента только потому,
что известно его определение.

Примеры из Aftertaste:

- Интерфейсы `EntryDraft` и `Entry extends EntryDraft` описывают поля записи
  и добавляют идентификатор сохранённой записи. Во Vue типизированы props,
  события и реактивное состояние.
- Дженерик `apiRequest<T>(...): Promise<T>` позволяет одной функции запросов
  описывать разные типы результата: `Entry[]`, `Entry`, данные пользователя.
  `ref<Entry[]>([])` задаёт тип элементов изначально пустого массива.
- `Partial<Record<ContentType, readonly string[]>>` описывает словарь жанров:
  ключи ограничены категориями, но данные могут быть не для всех категорий.
- `Exclude<ContentType, 'song' | 'album'> | 'music'` описывает категории
  каталога, где два музыкальных формата объединены в одну кнопку.
- `as const` и `(typeof contentTypes)[number]['value']` выводят допустимые
  категории из справочника, чтобы не поддерживать отдельный список строк.
- Предикат `isMusicType(type): type is 'song' | 'album'` сужает тип после
  проверки значения.
- Фронтенд наследует `strict: true` из конфигурации `@vue/tsconfig`.
  Дополнительно включён `noUncheckedIndexedAccess`.

### Дженерики и граница проверки данных

Упрощённый пример использования существующей функции запросов:

```ts
const entries = await apiRequest<Entry[]>('/entries')
// entries: Entry[]
```

`T` — параметр типа. Здесь вызывающий код выбирает `Entry[]`, и функция
возвращает `Promise<Entry[]>`. Это сохраняет тип результата для дальнейшего
кода, но не доказывает, что сервер действительно вернул массив записей.
Для внешних данных нужны проверки во время выполнения. В проекте серверный
`validateEntry` принимает `unknown` и проверяет поля входящей записи.

### Вопросы и ответы

**Что даёт strict?**  
Включает группу строгих проверок, в том числе `noImplicitAny` и
`strictNullChecks`: запрещает неявный `any` в соответствующих ситуациях
и требует учитывать `null` и `undefined`. Явный `any` он не запрещает.
Отдельные опции этой группы можно переопределить.

**Входит ли noUncheckedIndexedAccess в strict?**  
Нет, его включают отдельно. При чтении потенциально отсутствующего элемента
массива или значения по индексной сигнатуре результат учитывает `undefined`.
Например, `entries[0]` для `Entry[]` имеет тип `Entry | undefined`.

**Что такое сужение типа?**  
Уточнение типа на основании проверки в текущей ветке выполнения.
Например, после `if (entry.rating !== null)` поле `rating` из
`number | null` становится `number` внутри ветки.

**Чем unknown отличается от any?**  
`unknown` требует проверки или другого обоснованного уточнения типа перед
обращением к его свойствам. `any` позволяет такие операции без проверки
и ослабляет проверку использующего его кода.

**Что делают Pick и Omit?**  
`Pick<T, K>` выбирает свойства `K` из `T`, `Omit<T, K>` исключает их.
Например, `Pick<Entry, 'id' | 'title'>` описывает краткое представление записи,
а `Omit<Entry, 'id'>` — её поля без идентификатора. Это учебные примеры,
а не утверждение, что такие типы сейчас используются в проекте.
